# 기능 개발과 UI/UX 인계 절차

기능 범위·목업·화면 동작·서버 계약을 연결한 뒤 구현하고 검증하는 순서를 정한다.

## 적용 상황

새 기능·오류 수정·화면 변경을 맡은 개발자와 AI가 사용한다. 작업 단위는 사용자 흐름 하나다.
서버 함수나 위젯만 작성하고 기능 완료로 처리하지 않는다. 기준 진입점은 [AGENTS](../../AGENTS.md)다.

## 실행 전 확인

`git status --short`와 관련 diff를 읽어 다른 작업자의 변경을 확인한다. 해당 F-ID, 제품 정책,
UI-ID와 목업 판본, 현재 구현 차이 R-ID, 검증 V-ID를 확인한다. 확인한 내용을 작업 설명에 남긴다.

문서의 역할은 다음과 같다.

| 질문 | 위치 |
|---|---|
| 이번 제출 범위인가 | [기능 범위](../scope/today-meal.md) |
| 언제 저장하고 무엇을 취소하는가 | [제품 정책](../product/proposal.md) |
| 어떤 화면을 구현하는가 | [목업 인계](../../mockup/README.md) |
| 버튼·상태·오류·뒤로는 어떻게 동작하는가 | [UI 계약](../ui/mobile.md) |
| 데이터와 책임은 어디에 있는가 | [아키텍처](../architecture/README.md) |
| 무엇이 아직 안 되는가 | [작업표](../plan/hackathon-3day.md) |
| 어떤 증거가 있어야 완료인가 | [검증 기준](../verification/mvp.md) |

발표 자료·이전 실험 목업·보존 기록을 현재 구현 지시서로 사용하지 않는다.

## 절차

### 1. 사용자 흐름과 화면 계약 확인

작업 설명에 다음 한 묶음을 적는다. 별도 보고서를 매번 만들 필요는 없다.

```text
기능: F-ID / 구현 차이: R-ID
화면: UI-ID / 목업 판본 또는 파일 해시
사용자 시작 상태 → 행동 → 보이는 결과 → 다음 상태
저장되는 것 / 저장되지 않는 것
오류·시간 초과·뒤로·재시도·되돌리기
필요한 서버 데이터와 현재 빠진 계약
검증: V-ID / 자동·실기기·화면 비교 방법
```

목업에 없는 예외 상태는 UI 계약을 적용한다. 새 정책이 필요하면 문서에 제안·영향을 먼저
드러내고 해당 판단만 요청한다. 이미 확정된 시안·캐릭터·탭을 매 기능마다 새로 만들지 않는다.

### 2. 계약과 구현

화면이 요구하는 데이터를 먼저 확인하고 서버 스키마·DB·앱 모델을 함께 설계한다.
서버 검증과 API를 구현한 뒤 앱에 연결하되 사용자 경험을 서버 구현 편의로 축소하지 않는다.
API 구조의 정본은 schemas와 Swagger다. 문서는 데이터 의미·불변 조건·목표와 현재의 차이를 설명한다.

모델 출력은 제안으로 검증한다. 요청 ID는 재시도에서 유지한다. 화면 상태와 오디오 상태를
분리하고 성공·부분 성공·질문·실패를 다른 결과로 취급한다. 임시 더미를 운영 경로에 남기지 않는다.

### 3. 화면 비교와 사용자 시나리오

목업과 같은 재고·날짜·화면 크기로 비교한다. 정보 순서·주 행동·캐릭터·타일·탭·상태 표현을
확인하고 스크린샷을 남긴다. 목업에 없는 빈 상태·권한 거부·네트워크 실패·큰 글자도 확인한다.
데이터 변경 흐름은 DB 수량·이력·홈·목록·메뉴의 갱신을 함께 검증한다.

### 4. 검증과 인계

`sh scripts/verify.sh`를 실행하고 통과·실패·skip을 구분한다. 문서 변경은
`engsys docs check --project .`와 개별 문서 편집 검토를 수행한다. 새 소스·자산을 Git에 포함하고
재현성 검사를 통과시킨다. 실기기 확인은 자동 테스트와 별도다.

작업표의 상태와 증거 경로를 갱신한다. 코드·계약·목업 변경·검증 결과를 같은 설명 가능한
변경 묶음으로 남긴다. 사용자 승인 없이 커밋·배포가 자동 완료됐다고 보고하지 않는다.

## 성공 확인

| 상태 | 필요한 증거 |
|---|---|
| 대기 | 요구·차이·다음 작업이 식별됨 |
| 구현 중 | 코드가 있으나 계약·연결·검증이 남음 |
| 자동 검증 | 해당 테스트와 분석 통과. 실기기 미확인이면 기능 완료 아님 |
| 실기기 검증 | 대상 OS·기기·조건·기대/실제·화면 증거 확보 |
| 완료 | F-ID 완료 기준과 V-ID를 충족. 문서·소스가 같은 기준으로 재현됨 |

오류가 있어도 문서 정비 자체는 완료할 수 있다. 그 경우 요구를 낮추지 않고 코드의 미충족을
작업표에 명시한다. “문서 완료”와 “앱 기능 완료”를 같은 상태로 사용하지 않는다.

## 실패와 복구

동작이 계약과 다르면 테스트를 계약에 맞게 고치거나 구현을 수정한다. 기존 코드를 통과시키기
위해 요구를 조용히 바꾸지 않는다. 실기기가 없으면 미실행으로 기록하고 기기 증거를 만들지 않는다.
동시 수정이 보이면 맡지 않은 파일을 덮어쓰거나 되돌리지 않고 최신 diff를 확인한다.

검증 중 소스가 바뀌었으면 최종 변경분에 해당하는 검사를 다시 실행한다. Git 무시 규칙 때문에
앱 소스가 빠지면 규칙을 좁히고 해당 파일만 추적 대상으로 추가한다. `.env`·캐시·DB 자료를
함께 강제 추가하지 않는다. 영속 DB 초기화는 일반 복구 수단이 아니며 데이터 보존을 먼저 확인한다.
