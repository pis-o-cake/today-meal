# 0001. MVP 기술 설계

[기능 범위](../scope/today-meal.md)의 필수 16개를 3일 안에 완성하기 위한 기술 선택을 정한다.
음성 입출력·모델·저장소·배치를 한 번에 정하는 이유는 넷이 서로를 구속하기 때문이다 — 모델을
서버에 둘지가 키 관리를 정하고, 키 관리가 배치를 정하고, 배치가 저장소를 정한다.

**이 문서는 아직 `draft`다.** 여기 적은 선택은 실기기 스파이크(SP-1~SP-5)로 검증되기 전까지
확정이 아니다. 검증이 끝나면 `implemented`로 동결하고, **그 뒤의 변경은 [ADR](../adr)에 적는다.**
데이터 모델은 [0002 데이터 모델 설계](0002-database.md)가 갖는다.

## 제안 요약

### 결정 초안

| 질문 | 선택 | 한 줄 근거 |
|---|---|---|
| 앱과 서버를 나눌까 | **나눈다.** Android + FastAPI | 3일 중 가장 많이 고칠 코드가 프롬프트와 검증 규칙이다. 서버에 있으면 재시작만으로 반영된다 |
| 재고 계산은 어디서 | **서버만.** 앱에 복제하지 않는다 | 같은 규칙이 두 곳에 생기면 어느 쪽이 맞는지 판정할 수 없다 |
| 모델 제공자 | **Gemini 하나** | 영상 분석이 Gemini로 고정되므로 명령 해석까지 묶어 연결부를 하나로 줄인다 |
| 웨이크워드 | **기기 내장 인식 반복 청취 + 문구 매칭.** 호출어 "자비스" | Porcupine 무료 티어 종료, sherpa-onnx 는 실기기에서 모델 로드 중 프로세스가 죽었다. 셋째 선택지다 |
| 전사·낭독 | **Android 내장 서비스** | 호출 이후 명령이 짧아 전용 API의 정확도 이득이 계약·키·비용보다 작다 |
| 저장소 | **PostgreSQL 16** | 멱등 키 `UUID`, 별칭 `TEXT[]`+GIN, 제안 보관 `JSONB`, 수량 `NUMERIC`이 모두 필요하다 |
| 주 기기 | **핸드폰.** 태블릿 상시 대기는 후속 | 검증 대상이 늘고, 장보기 중 사용이 열린다 |
| 앱 프레임워크 | **Flutter 하이브리드.** Android + iOS | 같은 코드로 폰·태블릿·양 OS. 태블릿 후속 방향이 프레임워크 교체 없이 이어진다 |
| 웨이크워드 범위 | **전경 한정** | 핸드폰에서 상시 대기는 성립하지 않는다. 백그라운드는 후속 |
| 앱 아키텍처 | **MVVM.** ViewModel 은 `ChangeNotifier`, DI 는 `get_it` | 마이크 소유권을 단일 상태기계로 모으고 View 가 상태 하나만 받아 그리게 한다 |
| 서버 아키텍처 | **도메인별 패키지** | 도메인 하나를 폴더 하나로 넣고 빼야 한다. 추가 범위를 지워도 필수가 돈다 |
| 인증 | **하지 않는다.** 간편 로그인은 식별만, 보안은 전부 배제 | 3일 안에 인증을 제대로 만들면 필수 기능이 줄고, 지금 확인할 가설이 아니다 |

### 아직 검증되지 않은 것

아래는 선택의 전제이며 실기기로 확인하기 전에는 근거가 아니다. 대응 스파이크가 막히면 이
문서를 고친다.

| 전제 | 확인 | 막혔을 때 |
|---|---|---|
| ~~핸드폰에서 한국어 커스텀 호출어가 감지된다~~ | 확인됨 | 내장 인식 반복 청취로 "자비스" 감지 확인 |
| ~~`porcupine_flutter` 가 양 OS 에서 마이크를 잡고 놓는다~~ | 폐기 | Porcupine 을 쓰지 않는다 |
| iOS 에서 같은 반복 청취가 동작한다 | 미확인 | 버튼 경로를 주 진입으로 승격 |
| **Xcode 없이 iOS 를 낼 수 없다** | — | Xcode 설치(10GB·30분+)가 필요하다. 못 하면 iOS 를 후속으로 내린다 |
| 감지기 정지 후 내장 STT가 안정적으로 시작한다 | SP-2 | 전환 지연을 늘리고 버튼 경로를 보조로 유지 |
| 기기의 한국어 STT·TTS가 수량·날짜를 다룬다 | SP-3 | 음성 데이터 설치 안내, 미지원이면 텍스트 입력 확대 |
| Gemini가 등록·사용·보정·정정을 구조화 출력으로 가른다 | SP-4 | 프롬프트를 의도별로 쪼개고 확인 질문 비중을 늘림 |
| 같은 명령 ID 재요청이 중복 반영되지 않는다 | SP-5 | 명령 ID를 DB 유니크 제약으로 올림 |

## 설계

### 배치 — 앱과 서버를 나눈다

앱은 오디오 입출력과 화면만 갖고, 재고 계산·모델 호출·데이터 저장은 서버가 갖는다. 앱에 수량
계산과 날짜 비교 코드를 두지 않는다.

나눈 조건은 셋이다.

- LLM API 키를 APK에 넣으면 배포본에서 꺼낼 수 있다.
- 프롬프트와 명령 스키마를 3일 동안 계속 고친다. 앱에 있으면 매번 재빌드·재설치다.
- 재고 계산 규칙이 앱과 서버 양쪽에 생기면 어느 쪽이 맞는지 판정할 수 없다.

**버린 대안 1 — 앱 단독(Room + LLM 직접 호출).** 배포 리스크가 0이고 코드베이스가 하나다.
버렸다. 프롬프트 수정마다 재빌드가 붙고, 키가 APK에 남고, 재고 규칙을 나중에 서버로 옮길 때
사실상 다시 쓰게 된다.

**버린 대안 2 — 앱 단독으로 시작해 여유가 생기면 서버를 붙인다.** `Repository` 인터페이스를
처음부터 둘로 가르는 비용을 초반에 지불한다. 버렸다. 3일 일정에서 "여유가 생기면"은 오지 않고
쓰이지 않을 추상화만 남는다.

감수하는 비용: 배포 대상이 둘이고, 네트워크 없이는 재고 조회도 안 된다. 오프라인 캐시는 범위
밖이며 앱은 `Room`을 쓰지 않는다. 시연이 네트워크에 의존하므로 10/1에 녹화본을 준비한다.

### 모델 — Gemini 하나

명령 해석·메뉴 생성·영상 분석을 모두 Gemini로 처리한다. 서버에 `LlmGateway` 인터페이스를 두고
구현은 하나만 만든다. 모델 식별자는 설정값으로 분리한다.

필요한 일이 둘로 갈린다 — 짧은 한국어 명령의 구조화 해석과 공개 유튜브 URL에서의 레시피
추출이다. 뒤쪽은 공개 영상 URL을 영상 입력으로 직접 받는 경로가 사실상 Gemini뿐이다. 그 상황에서
명령 해석까지 묶으면 키 하나, 오류 처리 하나, 비용 측정 하나로 끝난다.

**버린 대안 — 명령 해석은 Claude, 영상 분석은 Gemini.** 기획서 §9의 원안이다. 버렸다. 필수
기능과 추가 기능이 서로 다른 제공자를 쓰게 되어, 추가 기능을 포기하면 Gemini 연결부가
사장되고 둘 다 살리면 3일 동안 연결부를 둘 유지해야 한다.

`LlmGateway` 인터페이스는 구현이 하나여도 유지한다. 한국어 명령 해석 품질이 미달일 때 교체
지점이 필요하고 그 비용은 인터페이스 하나 분량이다.

감수하는 비용: 제공자 종속이 생긴다. 발표에서 멀티 모델 라우팅을 구현했다고 말하지 않는다.
비용은 명령 해석과 영상 분석을 나눠 측정한다 — 한 제공자라도 호출 성격이 다르다.

### 음성 — 내장 인식 반복 청취 + 내장 STT·TTS

호출어 감지·전사·낭독을 모두 기기 내장 서비스로 한다. 대기 중에는 짧은 구간 청취를 이어
돌리며 전사에서 호출어를 찾고, 호출 이후의 명령은 같은 인식기로 한 번 더 받는다. 낭독은
`TextToSpeech`다.

호출어는 **"자비스"**다. 처음 잡은 "헤이 냉장고"보다 인식률이 높다 — 일반 명사 조합보다
고유명사 한 낱말이 짧고 또렷해 오인식과 지연이 줄어든다. 이전 호출어도 계속 받는다.

수단을 두 번 바꿨다. 계약([`WakeWordDetector`])은 그대로였고 구현만 갈아끼웠다.

| 시도 | 결과 |
|---|---|
| Porcupine | 무료 티어가 2026-06-30 종료. 기업 메일 가입만 가능하고 유료는 월 $899~ |
| sherpa-onnx 온디바이스 ASR | 갤럭시 SM-E426S 에서 **127MB 인코더 로드 중 프로세스가 시그널 없이 정리됨**(탐블스톤·SIGSEGV 없음, `libprocessgroup killed cgroup ... in 0ms`) |
| 내장 인식 반복 청취 | 동작 확인. 채택 |

sherpa-onnx 를 되살리지 않은 이유는 크래시만이 아니다. 고쳐도 **상시 127MB 상주**가 남고,
저가 기기 시연에서 같은 위험을 다시 진다.

상시 대기가 제품의 전제다. 버튼을 눌러 시작하는 흐름이면 "요리 중 손이 바쁘다"를 해결하지
못하므로 웨이크워드는 빼거나 미룰 수 없다. 반면 한국어 호출어를 직접 학습하려면 데이터
수집·학습·기기 최적화가 붙고, 3일 전체를 거기 쓰면 재고 관리와 메뉴 추천이 남지 않는다.

호출 이후의 명령은 짧다. 긴 문장이나 연속 받아쓰기가 아니므로 전용 STT API의 정확도 이득이
계약·키·비용·네트워크 왕복보다 작다.

**버린 대안 1 — openWakeWord / microWakeWord 직접 학습.** 학습 파이프라인 구축이 필수 슬라이스
여러 개와 맞먹는다.

**버린 대안 2 — 버튼 입력만 두고 웨이크워드를 후속으로.** 제품 가설 자체가 "손을 쓰지 않고 말로
기록한다"이므로 검증할 대상이 사라진다. 버튼과 텍스트 입력은 보조 경로로 상시 유지한다.

**버린 대안 3 — 상시 전사.** 원래는 "대기 중 STT·LLM 요청 0회"를 검증 기준으로 두었다.
**이 기준은 웨이크워드 수단이 두 번 막히면서 지키지 못했다.** 지금 구조는 대기 중에도 인식
서비스를 돌린다. LLM 요청 0회는 그대로 지킨다 — 호출어 매칭은 기기에서 문자열 비교로 한다.

대신 치르는 비용을 명시한다. 아래 「감수하는 비용」에 적었고, 발표에서 오프라인이라고
말하지 않는다.

제약이 하나 있다. **감지기와 `SpeechRecognizer`는 같은 마이크를 동시에 점유할 수 없다.** 소유권을
넘기는 지점이 이 제품의 최대 실패 지점이므로 마이크를 만지는 코드를 `VoiceSessionManager`
하나에 모은다. 상태기계는 [아키텍처](../architecture/README.md)가 갖는다.

감수하는 비용:

- 자격정보가 필요 없다. 외부 서비스 키를 쓰지 않는다.
- **대기 중에도 인식 서비스가 돈다.** 배터리와 데이터를 쓰고, 오디오가 기기 밖으로 나갈 수
  있다. `onDevice` 를 요청하면 시험 기기(SM-E426S)는 한국어 온디바이스 모델이 없어 매 구간
  거부(`error_language_not_supported`)하고 아무것도 듣지 못한다. 그래서 온라인 인식을 쓴다.
- 내장 서비스가 항상 기기 내에서 처리되는 것은 아니다. **완전 오프라인 STT라고 표현하지 않는다.**
- 구간 사이에 짧은 공백이 있다. 그 순간의 호출은 놓친다 — 전용 호출어 엔진과의 차이다.
- 취소 직후 곧바로 청취를 시작하면 Android 가 `error_client` 로 거부한다. 400ms 정리 시간을
  두고 넘긴다.
- 기기에 한국어 TTS 음성 데이터가 없으면 낭독이 안 된다.
- TTS 재생 완료와 오류 **양쪽** 콜백에서 감지기를 재기동한다. 한쪽만 걸면 실패 경로에서 대기로
  돌아오지 못한다.
- 잠금 화면·백그라운드 감지는 범위 밖이다. 전경 Activity에서만 감지한다.

### 저장소 — PostgreSQL 16

기획서는 "단일 기기 데모는 SQLite, 운영 배포는 영속 DB"로 열어두었다. 서버를 개발서버에 올리기로
정해졌으니 영속 DB 쪽이고 남은 선택은 종류다.

PostgreSQL을 고른 이유는 [0002 데이터 모델 설계](0002-database.md)가 쓰는 기능이 전부 필요하기
때문이다. 앱이 만든 멱등 키를 PK로 쓰려면 `UUID`와 `INSERT … ON CONFLICT`, 재료 별칭 검색에는
`TEXT[]` + GIN 인덱스, 모델의 원본 제안 보관에는 `JSONB`, 수량에는 `NUMERIC`이 필요하다.

**버린 대안 — SQLite.** 배열·`JSONB`·`NUMERIC`·`TIMESTAMPTZ`가 없어 전부 문자열로 우회해야 하고,
그 우회가 `units`와 잔량 계산에 그대로 들어온다. 서버가 있는 구성에서 파일 DB를 쓸 이유도 없다.

감수하는 비용: 개발서버에 PostgreSQL 컨테이너가 필요하다. 로컬 개발도 PostgreSQL로 한다 —
SQLite로 개발하고 PostgreSQL로 배포하면 타입 차이가 배포 시점에 드러난다.

### 앱 — 핸드폰 우선, Flutter 하이브리드

초기 설계는 주방 고정 태블릿의 Android 네이티브 앱이었다. 둘을 함께 뒤집는다.

**핸드폰으로 바꾼 이유**는 검증 가능성이다. 태블릿을 새로 두는 부담이 없으니 시연 자리에서
바로 써볼 수 있고, **장보기 중 부족 재료 확인**이라는 흐름이 새로 열린다. 그 흐름은
핸드폰만 할 수 있고 쿠팡 연계와 자연히 이어진다.

**Flutter 를 고른 이유는 태블릿을 포기하지 않기 위해서다.** 주방 고정 태블릿의 상시 대기는
제품 방향으로 유지하며, 같은 코드에 태블릿 레이아웃과 포그라운드 서비스를 더하면 된다.
네이티브로 폰을 만들고 나중에 태블릿을 붙이면 레이아웃만 다른 화면을 두 벌 유지하게 된다.

**버린 대안 1 — Android 네이티브 유지.** Compose 로도 폰·태블릿 반응형은 된다. 버렸다.
iOS 를 내려면 앱을 다시 써야 하고, 그 비용이 Flutter 학습 비용보다 크다.

**버린 대안 2 — React Native.** 음성 계층이 핵심인데 Porcupine 의 1급 플러그인이 Flutter 쪽에
있고, 오디오 권한과 네이티브 채널을 다룰 일이 많아 Flutter 가 유리하다.

쓰는 플러그인은 `porcupine_flutter` · `speech_to_text` · `flutter_tts` 다. 셋 다 네이티브
구현을 감싼 것이라 **기기별 동작 차이가 그대로 올라온다** — 한국어 지원 여부를 양 OS 에서
각각 확인해야 한다.

화면은 **핸드폰 세로를 기준으로 만들되 태블릿 가로로 확장 가능하게** 한다. 폭에 따라
1단/2단으로 갈리는 레이아웃 하나를 쓰고, 태블릿 전용 화면을 따로 만들지 않는다.

### 웨이크워드 — Porcupine 에서 sherpa-onnx 로

**Porcupine 을 쓸 수 없게 됐다.** 무료 티어가 2026-06-30 에 종료되어 기존 AccessKey 까지
정지됐고, 콘솔 가입이 업무용 이메일만 받는다. 유료는 월 $899 부터라 이 프로젝트의 값이
아니다. 이 문서가 `draft` 인 동안 드러난 외부 변화이므로 결정을 여기서 뒤집는다.

대신 **sherpa-onnx(k2-fsa)의 온디바이스 한국어 스트리밍 ASR** 을 돌리고 전사에서 호출어
문구를 찾는다. 키워드 스포팅 전용 경로도 있으나 사전학습 모델이 영어·중국어뿐이라 쓰지
못한다.

| 항목 | 값 |
|---|---|
| 패키지 | `sherpa_onnx`. Android·iOS·macOS·Windows·Linux·Web |
| 모델 | `sherpa-onnx-streaming-zipformer-korean-2024-06-16` |
| 크기 | int8 양자화본 약 132MB |
| 통신 | **없다.** 전부 기기 안에서 돈다 |

**버린 대안 1 — `flutter_wake_word`(davoice).** Android·iOS 를 지원하고 모델도 작다.
버렸다. 커스텀 호출어를 메일로 요청해 받아야 하고 가격이 공개돼 있지 않다. 이틀 안에
회신을 기다릴 수 없다.

**버린 대안 2 — openWakeWord 직접 학습.** 모델이 수 MB 로 가볍고 Piper TTS 에 한국어
음성이 있어 합성 데이터로 학습하는 경로가 있다. 버렸다. 임베딩 모델이 영어 음성으로
학습돼 한국어 품질이 검증되지 않았고 학습에 시간이 든다. **다만 예비일에 시도할 값은
있다** — 성공하면 132MB 가 수 MB 로 줄고, 실패해도 sherpa-onnx 가 이미 돌고 있다.
`WakeWordDetector` 인터페이스가 그 교체를 가능하게 한다.

**버린 대안 3 — Vosk.** 한국어 모델이 82MB 로 더 작다. 버렸다. Flutter 플러그인이 2년간
업데이트되지 않았고 일반 전사 WER 이 28.1% 다.

감수하는 비용은 **모델 132MB** 다. 시연에서 네트워크 없이 떠야 하므로 앱에 번들한다.
첫 실행에 모델을 앱 저장소로 복사하는 시간이 한 번 든다.

### 웨이크워드 — 전경 한정

핸드폰에서 상시 대기는 성립하지 않는다. 배경에서 마이크를 계속 열려면 포그라운드 서비스와
상시 알림이 필요하고 배터리를 먹으며, iOS 에서는 사실상 불가능하다.

그래서 **앱이 화면에 떠 있는 동안만 감지한다.** 조리 중 폰을 거치대에 올리거나 내려놓고
말로 조작하는 상황을 담는다. 배경으로 가면 감지를 멈추고 그 사실을 화면에 표시한다 —
대기 중인 것처럼 보이게 두지 않는다.

**발표에서 상시 대기를 구현했다고 말하지 않는다.** 전경 한정임을 밝히고, 주방 고정 태블릿의
상시 대기를 다음 단계로 설명한다.

버튼과 텍스트 입력은 보조 경로로 상시 유지한다. 전경 한정이라 호출어가 안 되는 순간이
네이티브보다 많다.

### 인증 — 하지 않는다

필수 범위에 로그인이 없다. 간편 로그인(F-22)은 **가장 낮은 우선순위의 추가 기능**이며 사용자를
식별하는 것까지만 한다. 보안은 의도적으로 전부 배제했다 — 범위의 정본은
[기능 범위](../scope/today-meal.md)의 「간편 로그인의 범위」다.

호출자 식별은 요청 헤더 `X-User-Id`로 받는다. **서버는 이 값을 검증하지 않는다.** 서명도 만료도
세션도 없고, 값을 바꿔 보내면 다른 가구의 데이터에 접근할 수 있다. 이것이 의도한 상태다.

이 선택을 문서에 크게 적는 이유는 둘이다.

- **발표에서 인증을 구현했다고 말하지 않기 위해서다.** 로그인 화면이 있으면 보안이 있다고
  오해되므로, 화면에도 식별 전용이라는 표시를 남긴다.
- 나중에 인증을 붙일 때 **무엇을 새로 만들어야 하는지**가 이 목록이다. 지금 없는 것이
  토큰 검증·세션·권한 검사·위조 방어 전부다.

`X-User-Id`가 없으면 기본 가구(`household_id = 1`)로 처리한다. MVP는 기기 한 대에서
쓰므로 로그인 없이도 전 기능이 돌아야 한다. 로그인은 기능을 막는 관문이 아니다.

**이 상태로 공개 배포하지 않는다.** 실제 사용자를 받기 전에 인증을 다시 설계하며, 그 변경은
설계가 동결된 뒤이므로 [ADR](../adr)에 적는다.

### 설계 동결 조건

이 문서가 `implemented`로 넘어가는 조건은 둘이다.

1. SP-1~SP-5가 실기기에서 실행되고 위 「아직 검증되지 않은 것」의 전제가 확인되거나 대체안으로
   교체된다.
2. [0002 데이터 모델 설계](0002-database.md)가 Alembic 마이그레이션으로 구현된다.

**동결 이후의 변경은 이 문서를 고치지 않고 [ADR](../adr)에 적는다.** 동결 전에는 ADR을 쓰지
않는다 — 설계가 흔들리는 동안 기록한 결정은 결정이 아니라 초안이고, 그 초안은 이 문서가 갖는다.
ADR이 답하는 질문은 "그 뒤로 왜 바뀌었는가"다.
