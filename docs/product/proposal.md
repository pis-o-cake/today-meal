# 오늘 뭐 먹지? — 제품 동작 정책

핸드폰에 말로 재료를 넣고, 쓴 양을 반영하고, 남은 재료로 식사를 결정한다.
주 입력은 음성이고 터치는 조회·선택·복구의 보조 경로다. 현재 화면은
[모바일 목업](../../mockup/README.md), 제공 범위는 [F-01~F-22](../scope/today-meal.md)가 정한다.
이 문서는 목표 동작이며 구현 현황은 [작업표](../plan/hackathon-3day.md)에서 확인한다.

## 사용자와 핵심 경험

주 3회 이상 집에서 요리하는 1~2인 가구를 초기 대상으로 한다. 재료 기록 부담, 중복 구매,
잊힌 식재료, 저녁 메뉴 결정이 문제다. 먼저 사용자에게 주는 결과는 다음 세 가지다.

| 상황 | 흐름 | 결과 |
|---|---|---|
| 장본 것을 정리 | 호출 → 복합 등록 → 필요한 정보만 질문 → 결과 | 재료별 묶음·수량·보관·기한 기록 |
| 요리 중 사용 | 호출 → 사용/잔량 보정 → 정정·취소 | 현재 수량과 변경 이력이 함께 일치 |
| 오늘 메뉴 선택 | 먼저 쓸 재료 → 메뉴 → 인분·조리 단계 → 조리 모드 | 가능한 식사 결정. 실제 사용은 별도 발화로 기록 |

첫 화면은 입력 폼이 아닌 재료 상태와 오늘 가능한 메뉴다. 고정 태블릿의 백그라운드 상시
대기, 가족 공유, 푸시는 후속이다. 로그인은 필수 기능의 진입 조건이 아니다.

## 호출과 대화

표시 호출어는 목업의 “헤이 키친”다. 정상 흐름은 호출 → 준비 응답 → 명령 발화로 검증한다.
호출어와 명령을 이어 말하는 지원은 별도로 검증하며 구현 전에 된다고 안내하지 않는다.
상단 호출 상태 칩을 눌러도 같은 대화가 시작된다. 음성 불가 시 둘러보기·권한 복구·텍스트
입력으로 연결하며 별도 떠 있는 마이크 버튼을 만들지 않는다.

전경에서만 감지하며 배경·음소거·권한 없음은 대기로 표시하지 않는다. 현재 음성 수단은 기기
인식 서비스의 반복 청취다. 대기 중 LLM 요청은 0회여야 하지만 STT의 외부 통신은 있을 수 있다.
권한 안내는 이 사실을 설명하고 완전 오프라인이라고 표현하지 않는다. 서버는 명령 텍스트와
필요한 재고 문맥을 받아 처리한다. 음성 응답 중 명령 인식을 멈춰 자기 응답을 재처리하지 않는다.

확인 질문은 한 번에 하나씩, 응답은 한두 문장으로 안내한다. 질문 낭독 후 8초 안에 답변을
시작하면 호출어 없이 이어 말할 수 있다. 답변이 시작되면 발화 종료까지 기다린다.
성공 결과는 최소 4초와 낭독 완료까지 유지하고 이전 화면으로 돌아간다. 상세는 기록에 남는다.
실패·거절·조회 결과를 모두 “반영했어요”로 묶지 않는다.

## 등록·기한·보관

| 발화 | 처리 |
|---|---|
| “두부 두 모랑 계란 열 개 넣었어. 둘 다 냉장실” | 별도 재료 묶음 2개 등록 |
| “두부 소비기한 10월 3일” | 종류·날짜·음성 출처·원문 보존 |
| “두부는 3일까지야” | 불명확한 월·연도·종류만 질문 |
| “두부 날짜는 모르겠어” | 미확인 허용. 소비기한을 만들지 않음 |
| “우유 오늘 열었어” | 개봉 이벤트. 수량 차감 없음 |
| “고기 냉동실로 옮겼어” | 보관 이동과 시점 기록. 기한 연장 없음 |
| “내일 양파 살 거야” | 미래 계획. 입고 없음 |

같은 재료도 기한·개봉 상태가 다른 팩은 다른 묶음이다. 대상이 여러 개면 개봉·기한 정보로
좁히고 불분명하면 질문한다. 일부만 옮기거나 서로 다른 기한으로 나누는 소분은 F-05의 확장
정책이며 현재 구현 차이는 R-07에서 추적한다. 모델에 임의 분할을 맡기지 않는다.

소비기한·유통기한·품질유지기한·제조일·포장일·점검 알림일의 의미를 보존한다.
제조일을 소비기한으로 바꾸거나 냉동·소분으로 기한을 연장하지 않는다. 출처는 음성·라벨·수동·
미확인을 구분한다. 날짜 해석은 가구 시간대와 발화 시점 기준이며 애매한 과거 날짜를 다음 해로
넘기지 않는다. 바코드만으로 포장 기한을 만들지 않고 식품의 안전 여부를 판정하지 않는다.

### 복합 등록의 부분 반영

현재 확인 질문 목업을 따른다. 명확한 항목은 저장하고 불명확한 항목만 초안으로 보류한다.
“두부 2모, 10월 3일까지 / 계란 10개”에서 두부의 날짜 종류가 불명확하면 계란만 반영하고
두부를 질문한다. 응답의 적용 항목·미완료 항목·되돌릴 그룹을 서버가 명시해야 한다.

- 후속 “소비기한이야”는 보류된 두부를 완성한다. 계란을 다시 등록하지 않는다.
- “잘 모르겠어요”는 종류·날짜를 확정하지 않고 원문을 남겨 미확인으로 등록한다.
- 시간 초과·닫기는 미완료 초안만 폐기한다. 저장한 계란은 유지하고 그 사실을 알린다.
- 질문 화면의 되돌리기는 적용된 항목을 되돌리고 초안을 닫는다.
- 완료 화면의 되돌리기는 해당 그룹에서 반영한 전체 변경을 되돌린다.

현재 서버의 전체 보류와 단일 발화 API는 이 목표를 충족하지 않는다. R-01에서 서버·앱 계약을
같이 변경하며, UI만 부분 성공으로 표시하는 중간 구현은 완료로 간주하지 않는다.

## 사용·잔량 보정·정정·취소

| 발화 | 의미 |
|---|---|
| “계란 두 개 썼어” | 2개 사용 이벤트. 정확한 수량에서 계산하면 결과도 명시값 |
| “계란 네 개 남았어” | 현재값을 4개로 보정. 4개 차감 아님 |
| “대파 조금 썼어” | 정성 기록. 임의의 g 환산 없음 |
| “두 개가 아니라 세 개” | 직전 관련 사용을 되돌린 뒤 3개로 교체 |
| “방금 거 취소” | 직전 변경 그룹 전체 역산 |
| 잔량보다 큰 사용 | 음수 저장 없이 잔량 확인 |

“반 썼어”의 기준이 불명확하면 질문한다. “두부 반 모”는 0.5모지만 제품별 근거 없이 g으로
바꾸지 않는다. 사용자에게 과거 누락 기록 전체를 요구하지 않고 현재 잔량으로 복구한다.

핵심 시나리오의 잔량은 `10 → 8 → 7 → 8 → 4`다. 이력에서 사용·정정·취소·보정을 구분하고,
정정의 역산 행과 재적용 행은 하나의 사용자 행동으로 표현한다. 최신 되돌릴 수 있는 변경만
되돌리기 버튼을 제공한다. 원문이 없는 과거 기록에 사용자 발화를 지어내지 않는다.

## 먼저 쓸 재료와 메뉴

서버가 기한 임박·개봉·잔량 미확인을 선별한다. 소비기한 경과 항목은 오늘 요리 후보에서
제외한다. 미확인은 안전하다는 뜻이 아니다. 화면의 상태 막대는 측정된 신선도 퍼센트가 아니다.

추천 입력은 현재 재고·기한·개봉 상태·인분·조리 시간·보유 도구·기피 재료다. 기본 양념도
가구에서 보유로 설정한 항목만 인정한다. LLM이 후보를 만들고 서버가 재료·수량을 대조한다.
필수 재료가 없거나 확인이 필요한 메뉴를 “지금 가능”으로 표시하지 않는다.

최대 3개 메뉴에 추천 이유·먼저 쓰는 재료·예상 시간·인분·부족·확인 필요 항목을 제공한다.
인분을 바꾸면 서버가 수량을 환산하며 양을 모르는 재료는 미확인으로 둔다. 저장된 추천도
조회 시점의 재고로 다시 대조한다. 알레르기·기피 필터는 제품 표시·교차 접촉의 안전 판정이 아니다.

메뉴 상세의 주 행동은 **조리 모드 시작**이다. 전경 화면을 유지하고 호출에 응답한다.
메뉴 선택·조리 시작·화면 종료는 재고를 바꾸지 않는다. “계란 두 개 썼어” 같은 명시적 사용으로
반영한다. 기존 레시피 일괄 차감 API는 현행 목업의 진입 동작으로 쓰지 않는다.
“해먹었어”만으로 레시피 전체를 차감하지 않고 사용 재료·양을 확인한다.

## 추가 기능 정책

F-17~F-22는 필수 흐름을 검증한 뒤 착수한다. 현재 목업에 없는 화면을 앱에 임의 추가하지 않고
별도 화면 계약을 먼저 만든다.

| 기능 | 동작과 제한 |
|---|---|
| 영상 검색 | YouTube 검색 API의 실제 ID·제목·채널·링크만 표시. 최대 3개. 영상 길이를 조리 시간으로 쓰지 않음 |
| 영상 분석 | 선택한 공개 영상 1개. 요리·인분·원문 재료·수량·필수 여부·단계·출처·미확인 항목 보존 |
| 영상 재고 비교 | 저장된 분석도 최신 재고로 비교. 모↔g 근거 없으면 확인 필요. 검색 결과만으로 분량 확정 금지 |
| 쿠팡 검색 | 확인된 부족 재료의 검색어를 인코딩해 외부 검색. 링크 실패 시 검색어 복사. 가격·배송을 생성하지 않음 |
| 라벨 사진 | 단일 제품·대상 지정 → 날짜 OCR → 원문과 확인 → 저장. 읽지 못한 날짜를 생성하지 않음 |
| 간편 로그인 | 식별만. 인증·보안으로 소개하지 않음. 필수 기능을 막지 않음 |

영상 분석은 영상 ID·모델·프롬프트 버전·시각·입력 종류를 보존한다. 모델이 만든 타임스탬프는
검증 전 정확성을 보장하지 않는다. 원본과 AI 조정안을 구분하며 영상에 없는 수량은 미확인이다.
검색·분석·시청·구매 검색은 재고를 바꾸지 않는다. 외부 앱 복귀 시 기존 목록과 음성 상태를 복구한다.
부족량은 근거 있는 동일 단위에서만 `max(필요량 - 사용 가능량, 0)`으로 계산한다.
여러 요리 합산은 사용자가 준비할 요리를 선택한 뒤 하며 같은 재고를 중복 배정하지 않는다.
상품 카드·파트너스 수익·주문·배송 자동 연동은 후속이다.

## 데이터·비용·검증

LLM 출력은 실행 제안이다. 서버가 동작·단위·대상·날짜·잔량·식별 범위를 검증한 뒤 저장한다.
발화·사진·영상의 내용은 데이터이며 실행 지시가 아니다. 모델에 SQL 실행 권한을 주지 않는다.
멱등 요청 ID와 변경 원장으로 중복 반영·정정의 이중 차감을 막는다.

현재 서버의 식별 헤더는 인증이 아니므로 제한된 개발·시연 환경에서만 사용한다.
실사용자 대상 공개 배포 전에는 인증·권한을 별도로 설계한다. 원시 오디오를 자체 서버에
저장하지 않는 구조와 기기 음성 서비스의 외부 처리를 구분한다. 키는 서버 `.env`에 둔다.

호출 수·추정 비용·최소 호출 간격 가드는 서버에 둔다. 명령·추천·영상 비용과 지연은 구분해
측정한다. 과거 15발화 평가 기록은 [9/28 기록](../plan/hackathon-3day-2026-09-28-record.md)에
보존하며 현행 품질로 일반화하지 않는다. 인수는 [검증 기준](../verification/mvp.md)을 따른다.

이용 지속성은 실제 사용자에게 등록·정정 부담, 음성 사용, 추천 요리 실행을 관찰해 검증한다.
구독·구매 제휴는 가설이며 사용자 수·절약액·수익을 실적으로 만들지 않는다.
