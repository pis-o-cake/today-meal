# 3일 해커톤 실행 계획

[기능 범위](../scope/today-meal.md)의 필수 16개를 9/30 18:00까지 제출 가능한 상태로 만든다.
기능을 계층별로 쌓지 않고 **수직 슬라이스**로 자른다 — 슬라이스 하나가 끝나면 서버·앱·실기기가
함께 동작해 그 자리에서 보여줄 수 있다. 구조는 [아키텍처](../architecture/README.md)를 따른다.

계층별로 쌓으면 마지막 날까지 보여줄 것이 없고, 어디서 틀어졌는지도 늦게 안다. 슬라이스마다
실기기 확인을 붙이는 이유다.

## 기준 시점과 일정

기준일은 2026-09-28이며 이 시점의 코드는 없다. 개발은 오늘 오후부터 시작한다.

### 기기·프레임워크 전환 (9/28)

주방 고정 태블릿의 Android 네이티브에서 **핸드폰의 Flutter 하이브리드**로 바꿨다. 근거는
[기술 설계](../design/0001-mvp-technical-design.md)의 「앱 — 핸드폰 우선, Flutter 하이브리드」다.

| 영향 | 내용 |
|---|---|
| 서버 | **영향 없음.** API 계약이 같고 테스트 109건이 그대로 유효하다 |
| 앱 | Android 네이티브 골격 43파일을 버리고 Flutter 로 다시 쓴다 |
| F-01 | 상시 대기 → **전경 한정.** 핸드폰에서 상시 대기는 성립하지 않는다 |
| F-15 | 대기 대시보드 → 홈 화면. 앱을 열면 보이는 화면이다 |
| F-16 | APK → APK + iOS 빌드 |
| 후속 | 주방 고정 태블릿의 상시 대기를 후속 방향으로 유지한다 |
| 새 기회 | **장보기 중 부족 재료 확인.** 핸드폰만 할 수 있고 쿠팡 연계와 이어진다 |

버린 골격은 커밋 이력에 남아 있어 필요하면 되살릴 수 있다. `VoiceSessionManager` 의
마이크 소유권 상태기계와 그 단위 테스트 5건은 Dart 로 옮길 때 설계를 그대로 쓴다.

| 항목 | 결과 |
|---|---|

### S-00 에서 확인한 것

`검증` 은 실기기 확인 전 단계다. 개발 머신에서 확인한 것과 남은 것을 가른다.

| 항목 | 결과 |
|---|---|
| 14개 테이블 생성 | Alembic `upgrade head` 로 적용. `alembic check` 드리프트 0, downgrade→upgrade 왕복 정상 |
| DB 제약이 불변 조건을 막음 | 음수 잔량·기한 종류 중복·잘못된 상태값·명령 ID 중복이 모두 `IntegrityError` |
| 정정 시나리오 | 핵심 5단계를 이벤트 원장으로 실행해 잔량 `10→8→7→8→4` 와 이력 7건 확인 |
| 서버 왕복 | `/health` · `/api/household/me` · `/api/ingredient?q=파` 응답. 별칭 매칭 동작 |
| 미구현 표시 | 구현 전 엔드포인트가 501 과 담당 슬라이스 ID 를 돌려줌 |
| 검증 진입점 | `sh scripts/verify.sh` 로 서버 59건 · 앱 5건 통과 |
| APK | `assembleDebug` 성공 |
| **남은 것** | **실기기 설치와 태블릿에서의 서버 왕복.** 개발 머신 확인은 실기기 확인이 아니다 |

### UI 는 구조만, 시각은 계속 바뀐다

목업의 **UX**(흐름·정보 구조·상태)를 참고해 화면 구조를 잡았다. 시각 디테일은 계속 바뀔
것을 전제로 하며, 테스트는 구조가 무너지지 않는지만 본다 — 색이나 여백을 고정하지 않는다.

하단 탭 셋으로 나눈다. 대화는 탭이 아니라 오버레이다 — 호출어는 어느 탭에서나 받으므로
탭 하나를 차지하면 돌아갈 곳을 잃는다. 태블릿 폭에서는 하단 바 대신 좌측 레일을 쓰며,
같은 화면을 다른 내비에 꽂는다.

| 있는 것 | 없는 것 |
|---|---|
| `VoiceSessionManager` 상태기계와 단위 테스트 10건 | 플러그인 실제 배선 (S-01) |
| 반응형 기제 — 폭 기준·1단/2단·태블릿 레일 | 확정된 시각 디자인 |
| Repository 구현과 ViewModel 4개 | "해먹었어요" 사용량 반영 |
| 홈(신선도 밴드)·냉장고·기록·메뉴 상세·대화 오버레이 | 쿠팡 검색·대체 재료 (S-13) |
| 화면 구조 테스트 6건 | 디자인 다듬기 |

홈은 재고를 **신선도 밴드로 묶어** 쌓는다 — 지남·급함·챙길 것·여유·미확인. 급한 것이 위로
오고 빈 밴드는 내보내지 않는다. 등급은 **서버가 판정한 값을 그대로 쓴다.**

**태블릿 병행을 코드의 기제로 넣었다.** `core/design/breakpoints.dart` 가 폭으로 형태를
판정하고 `ResponsiveTwoPane` 이 1단과 2단을 가른다. 목업 화면이 이 위에 꽂히므로 태블릿
전용 화면을 따로 만들지 않는다. 경계 판정은 단위 테스트 4건이 지킨다.

### 슬라이스 하나를 끝내는 절차

1. 기능 범위에서 해당 ID의 완료 기준을 읽는다.
2. API·데이터·화면 규칙이 바뀌면 아키텍처 문서를 먼저 고친다.
3. 서버 → 앱 순으로 구현한다. 앱이 먼저 가면 계약이 앱 편의에 맞춰 휜다.
4. 실기기에서 완료 신호를 확인한다.
5. 코드와 문서 변경을 같은 커밋 묶음으로 남긴다.
6. 이 표의 상태를 갱신하고 막힌 것을 아래 절에 적는다.

`코드 작성` · `빌드 성공` · `시나리오 검증` · `실기기 확인`을 구분해 적는다. 실기기 확인까지
끝난 것만 `완료`다.

### 이번 계획에서 의도적으로 뺀 것

3일 차에 발표 자료를 만들지 않는다. 필수 기능과 배포에만 시간을 쓰고 발표는 10/1~10/2에 만든다.
제출물은 APK와 서버이며 발표 자료는 제출 대상이 아니다.

테스트는 재고 무결성에만 붙인다. UI 테스트와 커버리지 목표를 두지 않는다. 깨지면 숫자가
틀리는 곳 — `units` · `command` 검증 · 정정 역산 · 잔량 정합성 — 에만 `pytest`를 쓴다.

데이터 모델의 정본은 [데이터 모델 설계](../design/0002-database.md)다. 스키마를 바꿀 때는 Alembic 마이그레이션과 그 문서를 같은 커밋에 넣는다.
