# 3일 해커톤 실행 계획

[기능 범위](../scope/today-meal.md)의 필수 16개를 9/30 18:00까지 제출 가능한 상태로 만든다.
기능을 계층별로 쌓지 않고 **수직 슬라이스**로 자른다 — 슬라이스 하나가 끝나면 서버·앱·실기기가
함께 동작해 그 자리에서 보여줄 수 있다. 구조는 [아키텍처](../architecture/README.md)를 따른다.

계층별로 쌓으면 마지막 날까지 보여줄 것이 없고, 어디서 틀어졌는지도 늦게 안다. 슬라이스마다
실기기 확인을 붙이는 이유다.

## 기준 시점과 일정

기준일은 2026-09-28이며 이 시점의 코드는 없다. 개발은 오늘 오후부터 시작한다.

| 날짜 | 구간 | 목표 |
|---|---|---|
| 9/28 (월) | 오후~심야 | 골격 · 음성 파이프라인 · 자연어 등록 |
| 9/29 (화) | 종일 | 조회 · 사용 · 보정 · 정정 · 취소 · 메뉴 추천 |
| 9/30 (수) | ~18:00 | 기한 카드 · 대시보드 · 배포 · **제출** |
| 10/1 (목) | 예비 | 버그 수정 · 시연 리허설 · 추가 기능 |
| 10/2 (금) | 시연 | 발표 및 시연 |

발표 자료는 제출 이후에 만든다. 9/30까지는 제품에만 시간을 쓴다.
[발표 계획](../product/presentation-plan.md)과 [HTML 브리프](../product/html-brief.md)는
10/1 이후 실제 구현 결과로 갱신한다.

## 작업표

담당은 전부 개발자이며 구현은 Claude Code와 함께 진행한다. 상태는 `대기 / 진행 / 검증 / 완료`
넷만 쓴다.

### 0일 차 전제 — 스파이크

본 구현 전에 확인한다. 하나라도 막히면 그 슬라이스의 설계가 바뀌므로 코드를 쓰기 전에 끝낸다.
합계 2시간 안쪽으로 묶고 길어지면 대체안으로 넘긴다.

| ID | 확인할 질문 | 막혔을 때 | 상태 |
|---|---|---|---|
| SP-1 | 태블릿에서 한국어 커스텀 호출어가 감지되는가 | 지원 호출어로 교체하고 문서·화면에 반영 | 대기 |
| SP-2 | 감지기를 멈춘 뒤 내장 STT가 안정적으로 시작하는가 | 신호음·전환 지연을 늘리고 버튼 경로를 보조로 유지 | 대기 |
| SP-3 | 기기의 한국어 STT·TTS가 수량·날짜를 다루는가 | 음성 데이터 설치 안내, 미지원 시 텍스트 입력 경로 확대 | 대기 |

않았으면 상태는 `대기`이며 완료로 적지 않는다.

### S-00 에서 확인한 것

`검증` 은 실기기 확인 전 단계다. 개발 머신에서 확인한 것과 남은 것을 가른다.

| 항목 | 결과 |
|---|---|
| 14개 테이블 생성 | Alembic `upgrade head` 로 적용. `alembic check` 드리프트 0, downgrade→upgrade 왕복 정상 |
| DB 제약이 불변 조건을 막음 | 음수 잔량·기한 종류 중복·잘못된 상태값·명령 ID 중복이 모두 `IntegrityError` |
| 정정 시나리오 | 핵심 5단계를 이벤트 원장으로 실행해 잔량 `10→8→7→8→4` 와 이력 7건 확인 |
| 서버 왕복 | `/health` · `/api/household/me` · `/api/ingredient?q=파` 응답. 별칭 매칭 동작 |
| 미구현 표시 | 구현 전 엔드포인트가 501 과 담당 슬라이스 ID 를 돌려줌 |
| 검증 진입점 | `sh scripts/verify.sh` 로 서버 59건 · 앱 5건 통과 |
| APK | `assembleDebug` 성공 |
| **남은 것** | **실기기 설치와 태블릿에서의 서버 왕복.** 개발 머신 확인은 실기기 확인이 아니다 |

### 슬라이스 하나를 끝내는 절차

1. 기능 범위에서 해당 ID의 완료 기준을 읽는다.
2. API·데이터·화면 규칙이 바뀌면 아키텍처 문서를 먼저 고친다.
3. 서버 → 앱 순으로 구현한다. 앱이 먼저 가면 계약이 앱 편의에 맞춰 휜다.
4. 실기기에서 완료 신호를 확인한다.
5. 코드와 문서 변경을 같은 커밋 묶음으로 남긴다.
6. 이 표의 상태를 갱신하고 막힌 것을 아래 절에 적는다.

`코드 작성` · `빌드 성공` · `시나리오 검증` · `실기기 확인`을 구분해 적는다. 실기기 확인까지
끝난 것만 `완료`다.

### 이번 계획에서 의도적으로 뺀 것

3일 차에 발표 자료를 만들지 않는다. 필수 기능과 배포에만 시간을 쓰고 발표는 10/1~10/2에 만든다.
제출물은 APK와 서버이며 발표 자료는 제출 대상이 아니다.

테스트는 재고 무결성에만 붙인다. UI 테스트와 커버리지 목표를 두지 않는다. 깨지면 숫자가
틀리는 곳 — `units` · `command` 검증 · 정정 역산 · 잔량 정합성 — 에만 `pytest`를 쓴다.

데이터 모델의 정본은 [데이터 모델 설계](../design/0002-database.md)다. 스키마를 바꿀 때는 Alembic 마이그레이션과 그 문서를 같은 커밋에 넣는다.
